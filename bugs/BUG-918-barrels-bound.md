# BUG-918 Barrels bound as stockpile containers: the release never said why; on i4 every candidate pile accepts drink and is skipped by design (diagnostics + cycle fix, NOT a cure)
Status: partly fixed (offline, live-untested): diagnostics and the daily lower / restore cycle fixed; the i4 binding itself is NOT freed by this change
Severity: high (i4 brews little; drink 57 -> 343 d only by caravans or luck)
Found: Run 17 i4 Girderroots y491, kernels 13700af3 / 8c553a52, DF E:/DF-test4. `why brew`: 'DF cancelled brew drink ... Needs empty food storage item'. `why items:barrels --raw`: '115 of 121 empties are registered in the storage.container_item_id of a stockpile', cont_free 0 (kern.log:235 '1 usable of 118 empty barrels or pots (88 held by stockpiles as their containers)'); BREW_CANCEL_SNAPSHOT #42971 `loc` `dfllm-stock=89;dfllm-drink=1;dfllm-start=1`, 91 free empties. A MakeBarrel x10 raised the empties 114 -> 116 only. No PILE_BARREL_RELEASE event on any of the four forts.
Module: `lua/dfllm/economy.lua` (`M.pile_release`, `M.release_none`, `M.release_watch`, `M.release_emit`, `M.cx_end`, `M.brew_watch`, `M.watch`), `dfpilot/schema.py`

## Proven / not proven
Proven (logs and code):
1. The container gate was OFF 196.44M-196.51M and 197.0M-198.1M (kern.1.log:776, 859, 1785) and ON from 198106769 (kern.log:1050). The 'window stays at 20' of the diagnosis is not a counter fault: `cxn` of BREW_CANCEL_SNAPSHOT is the size of the cancel-moment ring; the window count is `cancels` (12-53).
2. The release already RAN with the gate on (kern.log:2011: every pile kept). The piles holding the registered empties are `dfllm-stock` piles named in the samples (#19359 / #19482 max_barrels 9, #19462 max_barrels 27; `why pile:19359`: food pile, 0 full barrels, 1 empty) and they ACCEPT DRINK. `act.pile_barrels release` (act.lua:1514-1540) leaves every pile that accepts drink alone ('accepts drink: not changed in this round'), so on i4 the release finds nothing it may lower. That is by design (a pile that takes drink needs its barrels for the drink; kern.1.log:1671 shows the one pile it did see, #17706 `dfllm-start`, kept for that reason).
3. The release ran only inside the daily run with the census' start tick as its clock (`r.now`), inferred to be up to a few hundred game days old on this fort (no log shows it), and a call that lowered nothing wrote nothing: 'no pile qualified' looked like 'never ran'.
4. Cycle (found by the verifier, test below): the release's lowerings are also stored in `p.pilecap`; `M.cx_end` (no brew order, containers back, no cure) restored them but left `p.relpiles` / `p.relmeas`, so the next daily look lowered the same piles again: lowered / restored every game day (7 lowerings in 9 days in the test on the previous commit).

NOT proven and NOT done: that lowering a drink-accepting pile's barrel limit would make DF drop the registered empties from `storage.container_item_id`, and that doing it would not strip storage for filled goods (a pile that accepts drink / food needs barrels for its contents; the only value that unbinds an empty is the registered-full count, 0 or close for these piles, which would stop the pile taking drink barrels at all). No verified safe way exists offline, so NO code unbinds registered empties from drink-accepting piles. Whether the `dfllm-stock` piles should stop accepting drink is a stockpile-settings decision that needs a live look first (BUG-844: cures act only with DF's reason). This bug stays a diagnosis, not a cure, for the i4 binding.

## Fix (what changed)
1. `M.release_watch` (called from `M.watch`): the EXISTING `M.pile_release` once per game day at the REAL tick with the kernel's own state and census (same mechanism: BUG-844 gate, BUG-867 hysteresis, `relstop`, 14-day bound, d1 / d7 measurement); once it ran, `brew_watch` no longer calls it with the run's stale clock (`st.relwatch`).
2. `M.release_none`: a call with the gate open and registered empties that lowered NO pile (and no lowering in progress) emits PILE_BARREL_RELEASE `phase none` once per game week: registered empties (`reg0`), free empties (`free0`), piles looked at (`kept`), failed writes (`failed`), cancels (`cx0`), and in the text the count of piles AND of registered empties per reason ('3 accepts drink (115 empties)'). kern.log gets every kept pile with its own reason (`pile barrel release kept (i/n): <id> <name> limit L empties E: <reason>`, ten piles to a line, five lines at most), no longer only the first accepts-drink pile.
3. No daily scan: a call that lowered nothing sets `st.relidle` (REL_IDLE_D = 7): `act.pile_barrels release` (and its registry scan) is not called again for a game week. `brew_watch` sets `st.relhold` (30 days at most) when no brew could run (no Still, order or plant): no lowering for nothing.
4. `M.cx_end`: pile limits it gives back are forgotten as releases (`p.relpiles`, `p.relmeas` entries removed, no verdict on a restored pile) and the release rests `REL_IDLE_D` days (`p.relnext`).
5. `M.release_emit`: `free0` / `free1` / `free7` beside the registered empties and the cancels for a lowering that does happen (non-drink kernel piles).
Never dumped, destroyed or written: items, `container_item_id`; player piles are not touched.

## Live-Erwartung
i4: within one game day of the container reason being on, kern.log 'pile barrel release kept (1/N): ... dfllm-stock limit 9 empties 1: accepts drink ...' for every pile and ONE PILE_BARREL_RELEASE `phase none` per game week with `reg0` ~115, `kept` ~90 and the text '90 accepts drink (115 empties)'; no `act.pile_barrels release` repeat in the idle week. That settles which piles hold the empties and why none is lowered; it does NOT free the barrels, and brews still stall on i4 until a verified decision about the drink-accepting stock piles is made. A fort with non-drink kernel food piles holding registered empties: `lowered`, `d1`, `d7` with `reg1` / `reg7` below `reg0` and `free7` above `free0` prove the lowering; `reg7 >= reg0` gives 'DF kept the registration', the limits go back and nothing is lowered again.
