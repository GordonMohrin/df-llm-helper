# BUG-917 Autochop's expected logs of designated, unreachable trees keep it from designating reachable ones (WOOD_UNMARK)
Status: fixed (offline, live-untested)
Severity: high (i4 / i1 without wood for game years)
Found: Run 17, 26.11., kernel 2d71d780, DFHack `autochop status` (read only). i4 Girderroots: keeping log counts between 109 and 199, accessible logs 0, inaccessible logs 348, accessible trees 1032, designated trees 6, expected logs from designated trees 220, total trees harvested 62 (unchanged for 8 game years); WOOD_STUCK #37340 `ff 6, fo 6` 'all 6 open FellTree jobs lie off the citizens' walk group'; 17 free axes. i1 Diedplank: band 89-179, accessible trees 1035, designated 7, expected 246, harvested 33, FellTree n=7 unreachable. Counter-example i2 Whirledrampart (wood works): inaccessible trees 0, designated 1, expected 3, accessible logs 1226.
Module: `lua/dfllm/economy.lua` (`M.wood_unmark`, `M.wood_unmark_follow`, `M.marked_trees`, `M.pts_far`, `M.wood_stuck`), `lua/dfllm/act.lua` (`tree_unmark`), `dfpilot/schema.py`, `lua/dfllm/util/contract.lua`, `docs/v2/CONTRACTS.md`

## Proven / not proven
Proven: the numbers above, and that every open FellTree job lies off the citizens' walk group (kernel read). Both stuck forts have expected logs from the designated trees (220, 246) above the max threshold (199, 179). Not proven: that the plugin stops designating because expected >= max. The DFHack source of autochop is not on this machine (E:/DF-test4/hack holds docs and the compiled plugin only); docs/tools/autochop.txt says it 'designates appropriate trees for chopping' when the stock is low and that inaccessible trees are never designated, nothing about expected logs. The numbers fit; the live run decides. Also not proven: that `unmarkPlant` on a tree removes an already posted FellTree job (the plugin's own `autochop undesignate` uses the same API).

## Fix
1. `act.tree_unmark(positions)` (economy only, <= 200): `dfhack.designations.unmarkPlant` on the trees (`world.plants.tree_dry` / `tree_wet`) at the positions that are marked now (same pattern as `plant_ungather` for shrubs). Nothing is designated, dug or built.
2. `M.wood_unmark` (called by `M.wood_stuck` once WOOD_STUCK holds, only when every open FellTree job is off the walk group, only PEACE / RECOVERY): reads the marked trees (<= 300), asks `M.pts_far` (the group read of `cv_reach`, factored out; a tree answers the citizens' group when it touches it, an unknown group counts as reachable) and takes down exactly those off the walk group (<= `economy.wood.unmark_max` 120). Once per `unmark_days` (7), at most `unmark_runs` (3) per episode, `unmark = false` switches it off. Event WOOD_UNMARK `ph did`: `n` removed, `off`, `des` (marked before), `sample` (first 5 positions), `band` (the autochop band the kernel set), `run`. The plugin's own numbers (expected logs, harvested) are not readable by the kernel: kern.log says to read `autochop status`.
3. `M.wood_unmark_follow` (every `T.chop`): after `unmark_measure` (2) game days one measurement, event + kern.log line `ph result`: `des` marked trees now, `trees` felled (map tree count delta), `new` logs newer than the removal, `newnw` of them on tiles with no walk group (usable = new - newnw), usable logs now. If `newnw * 2 >= new` (new > 0) the removal STOPS for the episode (`ph stop`, `why unwalkable`), no further cure is guessed; so does the cap `unmark_runs` (`why runs`). The state ends with the stuck episode (usable logs again). Persisted m.economy `wunmark`.
4. 16b verifier point: the WOOD_STUCK text no longer says 'felling brings none'; it names the causes (logs / trees) and mentions new logs only when the census saw some.
