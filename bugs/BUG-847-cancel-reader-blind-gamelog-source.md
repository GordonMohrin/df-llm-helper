# BUG-847 The cancel reader saw nothing live: the tally stayed empty while gamelog.txt held 219 brew cancels in its last 400 lines
Status: fixed (offline, live-untested)
Severity: high
Found: Run 17d i4 Girderroots (main 4081ef70, E:/DF-test4), 24.11.2026 23:00: after ~25 game days the stall line said `raw stall brew: DF: no cancel reason seen`; `why brew` had no DF reason; `cx_gate` never opened. gamelog.txt: 110x '<name>, <profession> cancels Brew drink from plant: Needs empty food storage item.' and 109x '... Brew drink from fruit: Needs unrotten fermentable leaf or fruit.' in the last 400 lines.
Module: `lua/dfllm/gamelog.lua` (new), `lua/dfllm/economy.lua` (`M.gl_poll`, `M.cw_source`, `M.cw_health`, `cancel`, `M.step`, `M.jw_ctx`), `lua/dfllm/dfraw.lua` (`R.stall_line`), `lua/dfllm/jobwhy.lua` (`J.attach_df`, `J.line`), `config/baseline.json`, `dfpilot/fairplay.py`

## Root cause
Not the wording: `orderlib.cancel_parts` (orderlib.lua:166) parses both live sentences, CP437 name prefixes included (tests/lua/test_bug847_848_reader_pile.lua, first test). The sentences never arrive at it. The only source was eventful's REPORT (kern.lua:1773 `ev.onReport`, queue cap `CAD.eventq_max`, economy.lua `M.on.REPORT` -> `cancel`). Live evidence from i4's own logs: events.jsonl holds exactly 2 CANCEL_LOOP events in its whole life (`Plant seeds` tick 154664594, `Brew drink from fruit` tick 156471260; `cancel()` emits one per kind and game day from the 5th cancel of the day), none in the last ~1.2M ticks (1,000 game days), while gamelog.txt prints a cancel line for every worker that tries the job. So the REPORT path delivers at most a trickle (candidates: DF folds repeats of a job cancel into one report, the eventful queue drops when full, the plugin's poll skips reports DF already trimmed); which of these it is cannot be told offline, and it does not matter: a lossy source cannot be the only one. kern.log's `raw stall` line also had no way to tell 'DF cancelled nothing' from 'the reader is blind'.

## Fix
- `gamelog.lua`: an incremental, bounded reader of `<DF>/gamelog.txt`. First look at the END of the file (old lines are not today's); then at most `economy.cancel.gamelog_bytes` (131072) per look; only complete lines (a half line waits); a backlog above 1 MB (a long pause) is skipped and counted, never read; the file is never read whole (272 MB live). Truncation (size < offset) and replacement (the first 64 bytes differ) restart at 0; the `*** STARTING NEW GAME ***` marker drops the lines before it in the same look; CP437 bytes (>= 128) are cut to `?` in job and reason, names are never kept. The offset and the hex of the first 64 bytes persist in m.economy `gl` (once per game day), so a reload continues where it stood.
- Source arbitration (`M.cw_source`): `gamelog` while the file is readable and a new line arrived within 3 game days, else `report` (the eventful path, as before). The report handler counts into the tally only when the source is `report` (no double count); everything else `cancel()` does (CANCEL_LOOP, needs_cancel, sand / hard stone / wood hooks) is unchanged and still report driven.
- Health, never silent: `M.cw_health` -> 'DF cancel lines seen in window: N (source gamelog; X gamelog lines read, Y cancels)' or '(source report; gamelog missing: cannot open ...; K reports since load)'. It is in the weekly `raw stall` line (`DF: <reason or no cancel reason seen> | <health> | ...`) and in `why` (result field `dfh`; the line ends with it when DF has no reason). A change of the reader's state is one kern.log line ('gamelog reader: <path> ...', a warn with 'falls back to the eventful reports' when unreadable).
- Why the kernel reads the file and not the CLI: the kernel already reads plain files (io.lua, runner.lua, perf.lua) and gamelog.txt is DF's own text log of what a player sees on the announcement screen; fair play blocks `dfhack-run` calls and writes to dfllm-runtime, not reads. The CLI path (`dfpilot gamelog`, cli.py `run_gamelog`) reads the whole file with `read_text`, would need a running follow to feed an inbox command, and would leave the kernel blind while no CLI runs; the kernel needs the tally for its own gates (`cx_gate`).
